# ShopFlow

A small customer-support operations backend built with Python, FastAPI and PostgreSQL.

This is a learning/portfolio project. It deliberately uses ordinary, readable code:
- FastAPI routes handle HTTP requests.
- Pydantic schemas validate request and response data.
- SQLAlchemy models describe database tables.
- Service functions hold order rules.
- PostgreSQL stores customers, orders, tickets and audit events.

There is no AI dependency in this stage. The goal is to make the business operations reliable before adding a conversational interface or n8n workflows.

## Requirements

- Python 3.11+
- PostgreSQL 16+ (or a compatible recent version)
- Git (optional)
- VS Code (optional)

## Setup

### 1. Create the database

In `psql` or pgAdmin, run:

```sql
CREATE DATABASE shopflow_db;
```

### 2. Create and activate a virtual environment

Windows PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
```

macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies and configure the database

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Copy `.env.example` to `.env`, then replace `YOUR_PASSWORD` with your local PostgreSQL password.

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

macOS/Linux:

```bash
cp .env.example .env
```

If your PostgreSQL username, port or database name differs, update `DATABASE_URL`.

### 4. Create tables and sample records

```bash
python -m app.seed
```

The seed command is safe to run more than once. It creates the sample customers and orders only when they do not already exist.

### 5. Start the API

```bash
uvicorn app.main:app --reload
```

Open:
- API docs: http://127.0.0.1:8000/docs
- Health check: http://127.0.0.1:8000/health

## Sample data

The seed script creates:
- Alice Martin (`alice@example.com`) with two orders
- David Smith (`david@example.com`) with one pending order
- Emma Wilson (`emma@example.com`) with one delivered order

IDs are generated by PostgreSQL. Do not assume they will always be 1, 2, 3 and 4. Check the customer and order IDs in `/docs` or pgAdmin.

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Check API and database |
| POST | `/customers/` | Create a customer |
| GET | `/customers/{customer_id}` | Get a customer |
| GET | `/orders/{order_id}?customer_id=...` | Get an order belonging to a customer |
| POST | `/orders/{order_id}/cancel` | Check or confirm cancellation |
| POST | `/tickets/` | Create a support ticket |

### Example: create a customer

`POST /customers/`

```json
{
  "name": "Jordan Lee",
  "email": "jordan@example.com"
}
```

### Example: look up an order

`GET /orders/1?customer_id=1`

Use IDs from your own database.

### Example: check cancellation eligibility

`POST /orders/1/cancel`

```json
{
  "customer_id": 1,
  "confirm": false
}
```

If eligible, send the same request with `"confirm": true` to perform the cancellation.

Orders in `pending` or `processing` status can be cancelled. Shipped, delivered and already-cancelled orders cannot.

### Example: create a support ticket

`POST /tickets/`

```json
{
  "customer_id": 1,
  "order_id": 1,
  "subject": "Delivery question",
  "description": "The tracking page has not changed since yesterday.",
  "priority": "normal"
}
```

`order_id` can be `null` when the ticket is not about a specific order. Priority must be `low`, `normal` or `high`.

## Run tests

The automated tests use an in-memory SQLite database. They do not change your PostgreSQL development data.

```bash
pytest -v
```

## Important project limitations

This is a local development foundation, not a production-ready customer system.

Before real customer use:
1. Add authentication and authorization. The current `customer_id` parameters are for development and must not be treated as proof of identity.
2. Add Alembic migrations instead of relying on `create_all`.
3. Add stronger database constraints and concurrency protection for state-changing operations.
4. Add rate limiting, structured logging, monitoring and backups.
5. Review privacy, retention and security requirements before storing real customer data.

## Suggested next step

Build a conversation interface that calls these API endpoints. Keep order eligibility and cancellation rules in the backend; the chat interface should not decide whether an order can be cancelled.
